Two readers, same content

One page. Two very different readers.

BEFORE

One reader

An HTML/JS website built for a human: skimming headings, scanning for one paragraph.

No second reader existed — developers read the docs and wrote the integration themselves.

→
NOW

Two readers

A human still skims. But now an agent has to discover, authenticate, parse, and recover from errors on its own.

This is dual readership: the same page, read by two very different readers.

What docs are for

What API documentation actually has to do.

01

Endpoints & behavior

What the API does, described so the reader can call it correctly.

02

Parameters, schemas & auth

What it needs: request and response shapes, required fields, credentials.

03

Examples & error handling

What it shows: worked examples, and what happens when a call fails.

Key takeaway Documentation is the interface between an API and whoever has to use it correctly — not a description of the API for its own sake.
The agent-facing surface

What we create for agents.

01

llms.txt

A plain-text index at the root of the site, so an agent knows what exists before it starts guessing.

02

Per-page Markdown

The same content as the HTML page, stripped of navigation and JS chrome, so it is cheap to parse.

03

An MCP server

A tool the agent calls directly, like searchDocs, instead of scraping and re-parsing pages itself.

Key takeaway Three formats, one purpose: give the agent a shortcut past the parts of the page it cannot use.
How MCP works

So, what is an MCP server?

01

Host

The application the human uses: Claude, an IDE, or a custom agent.

02

Client

Lives inside the host and manages exactly one connection to one server.

03

Server

A program that exposes tools — for example, a search function the agent can call.

04

Transport

Messages travel as JSON-RPC, typically over HTTP.

Why it matters

Why MCP is good news for docs.

01

Queryable, not scraped

An agent calls a tool like searchDocs, instead of parsing raw HTML.

02

Answers stay grounded

Responses are scoped to what the docs actually say, not a guess.

03

One door, not one scraper each

A single server every agent can reuse, instead of custom scraping per integration.

But How do you keep all of that — the docs, llms.txt, the Markdown, and the MCP server — up to date?
The manual curating

Imagine curating this by hand.

01

Update the OpenAPI spec

The source everyone is supposed to trust.

→
02

Update the human docs

Rewrite the affected pages, and hope nothing was missed.

→
03

Update llms.txt & Markdown

If they exist, and if anyone remembers they are separate files.

→
04

Patch the MCP server

Re-implementing whatever changed, separately from the docs.

The failure mode Four surfaces, four owners, four chances to forget. Anything maintained by hand drifts.
