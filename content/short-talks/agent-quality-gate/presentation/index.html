The failure

The build stayed green.
The consumer still broke.

A coding agent renames a response field and marks a request field required. It updates its own unit tests to match. The build is green. Nothing local says a consumer just broke.

The idea

Five deterministic steps.
One Postman CLI command each.

1 · skills-check

postman skills status

not_available today — grey, excluded from the score

2 · contract-lint

postman spec lint

governance rules — shape, not compatibility

3 · tests

collection run --use-mock

JUnit + the committed collection vs. a mock of the new contract

4 · ai-readiness

spec ai-readiness

warn-only, how well an agent can use the API

5 · impact

context-graph ask

who depends on it — the one fuzzy, LLM-backed step

Score → letter rating A–E → hard blockers that override the score. Runs in CI, not on the agent's machine: it can't skip it, edit it, or see its secret.

What it costs

The limits this talk
doesn't hide.

skills-check is not_available

A real Postman CLI bug, not a design choice. Grey, excluded from the score, never a silent pass.

impact is the one fuzzy step

The breaking verdict is a deterministic diff. Who depends on it comes from an LLM-backed Context Graph query — it can still miss a consumer.

The gate never merges anything

It reports a verdict. A human, or a branch-protection rule, still has to act on it.

Objections

Two questions, every time.

"Lint passed — doesn't that mean the change was fine?"
No. Lint checks the shape of a contract against governance rules, not its compatibility with the version before it. That gap is exactly why there are five steps, not one.
"Does this block the merge?"
Not by itself. It's a CI check with a verdict — whether that verdict blocks a merge is a branch-protection setting on your repo, not something the gate enforces on its own.
Close

the code agrees with
